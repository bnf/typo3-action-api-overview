The TYPO3 Action API A typed API for the backend, integrations and AI agents.

An action is a typed PHP method that the backend, external applications and AI agents can call. TYPO3 validates the input and the output, documents the action and checks the access, so the action needs no controller.

#[AsAction(
    type: ActionType::fetch,
    name: 'my-extension/page/{uid}/titles',
    summary: 'Fetch the titles of a page',
    scopes: [ContentReadScope::class],
)]
public function titles(int $uid): array
{
    // your business logic
}

Problems and solutions

Today, each way to talk to TYPO3 has a separate implementation. With actions, all ways use one common model.

Each controller parses arguments, validates them and formats errors in a different way. A generic dispatcher handles all actions. TYPO3 validates arguments and results against a schema from the method signature. Integrations depend on extensions, and each extension builds and maintains separate endpoints. Every action of TYPO3 or of an extension has an HTTP endpoint below /typo3/api/. Each integration builds API keys, OAuth and fine-grained permissions again. EXT:hub offers OAuth 2.0 and static tokens. Scopes limit apps, and the permissions of the user always apply. Developers document endpoints by hand, if at all, and over time the documentation and the code differ. TYPO3 generates an OpenAPI 3.1 document from the code. Swagger UI shows the document. Assistants have no safe, standard way to read or change content for an editor. The built-in MCP server offers actions as tools. Agents act as the user, and the granted scopes limit the agents. The backend UI, integrations and automation each need separate glue code. Developers implement a feature once, as an action, and every channel can use the action.

Actions

An action is a public method of a service with the attribute #[AsAction]. The signature is the contract, and TYPO3 derives everything else from the signature once, when TYPO3 compiles the dependency injection container.

Hover over or tap a highlighted part to see what TYPO3 derives from the part.

final readonly class PageTitleAction
{
    public function __construct(
        private PageTitleRepository $pageTitles,
    ) {}

    /**
     * @return list<string>
     * @throws NotFoundError if the page does not exist
     */
    #[AsAction(
        type: ActionType::fetch,
        name: 'my-extension/page/{uid}/titles',
        summary: 'Fetch the titles of a page',
        scopes: [ContentReadScope::class],
    )]
    public function titles(
        int $uid,
        ActionContext $context,
    ): array {
        $titles = $this->pageTitles->findByPage($uid);
        if ($titles === []) {
            throw new NotFoundError('Page not found', 1791975434);
        }
        return $titles;
    }
}

The name is the identifier of the action and sets its route /typo3/api/my-extension/page/{uid}/titles. The name of the MCP tool is fetch_my_extension_page_by_uid_titles. The summary documents the action for developers in OpenAPI and for AI agents in the tool list. The caller must have all listed scopes. Otherwise TYPO3 rejects the call. The parameters define the input JSON Schema. TYPO3 reads the values from the route, the query string or the JSON body, validates them and converts them to PHP types. TYPO3 passes the ActionContext automatically and keeps the ActionContext out of the schema. The ActionContext holds the TYPO3 context, the user, the translator, the request and the granted scopes. PHPDoc types such as list<string> or array shapes define the output schema. TYPO3 validates the result before TYPO3 returns the result. The action must declare every error with @throws. TYPO3 returns NotFoundError as 404 and PermissionDeniedError as 403, and documents both errors in OpenAPI.

Channels

Each channel shows the example action as its consumer sees the action. No channel needs additional code.

Backend modules call actions through a small client. The client adds the bearer token of the logged-in user, so a session cookie alone is not sufficient.

import { action } from '@typo3/core/action/request.js';

const response = await action('/my-extension/page/{uid}/titles', { uid: '42' }).get();
const titles = await response.resolve();

External applications call the same route with a token from EXT:hub. A declared error comes back with its status code.

curl -H 'Authorization: Bearer <token>' \
    https://example.org/typo3/api/my-extension/page/42/titles

# 200 OK
["Home", "Startseite", "Accueil"]

# 404 Not Found
{"error": "Page not found"}

Stack

Each layer of the stack has one responsibility. Click a layer for details, or play a scenario to follow a request through the stack step by step.

The backend, external scripts and integrations, AI assistants and local coding agents use the same actions. No client needs a separate endpoint.

  • Backend JavaScript with @typo3/core/action/request
  • Any HTTP client, for example curl, generated OpenAPI clients and automation tools
  • MCP clients, for example Claude, MCP Inspector and other AI agents

Every action has a JSON endpoint below /typo3/api/, and the type of the action sets the HTTP method. TYPO3 also offers the same actions as MCP tools, over HTTP or locally through mcp:serve, and describes the actions in an OpenAPI 3.1 document at /typo3/api/schema.

Components of the layer are ActionHandler, MCP server, OpenApiBuilder.

Every call runs as a backend user. In the backend, the session identifies the user. External applications authenticate with a token from EXT:hub, through OAuth 2.0 or as a static token.

Scopes limit the actions that an application can call for the user, for example content:read or dashboard:write.

Components of the layer are Backend authentication, AppResolver, OAuth 2.0 server, ScopeRegistry.

The core knows every action and its JSON Schema. TYPO3 compiles the actions and the schemas once with the dependency injection container. For each call, the core does these steps:

  • check the needed scopes
  • validate the arguments and convert them to PHP types
  • call the action method with an ActionContext
  • validate the result against the output schema
  • map declared errors to status codes

Components of the layer are ActionRegistry, RequestHandler, ActionInvoker, Schema builder and hydrator.

Actions are methods of regular services with the attribute #[AsAction]. An action contains only the business logic, without request parsing, serialization or authentication.

TYPO3 ships actions for the dashboard, the page tree, file resources and records. The MCP server is also an action. Extensions add more actions.

Actions use the regular TYPO3 APIs. Because actions run as a backend user, page permissions, table and field access, workspaces and all other backend rules apply as in the backend.

TYPO3 derives the record schemas from TcaSchema, so the schemas describe the content model of each installation.

The page tree component calls the action with the JavaScript client:

action('/page/tree', { … }).get()

The client adds a bearer token from the backend document.

GET /typo3/api/page/tree matches the backend route that TYPO3 registered for the action.

The session cookie and the bearer token must belong to the same user, so other websites cannot call actions in the name of a logged-in editor.

TYPO3 grants all scopes that the editor can hold.

The action needs content:read, and the editor has this scope. TYPO3 validates the query arguments against the input schema.

TYPO3 converts the arguments to PHP types and calls the method with an ActionContext. The ActionContext holds the user, the scopes and the request.

The page tree action builds the tree items. The action knows nothing about HTTP.

The tree contains only the pages that the editor can see.

TYPO3 validates the result against the output schema and returns the result as JSON. The former internal AJAX route is no longer necessary.

curl -H 'Authorization: Bearer <token>' \
  https://example.org/typo3/api/dashboards

An administrator created the token for the app in the API Hub module.

The request reaches the same route as a request from the backend UI.

There is no backend session, so EXT:hub validates the token. The app must be enabled, and the secret of the app must be unchanged. EXT:hub loads the backend user that the app record selects.

The app gets exactly the scopes that the app record selects, for example dashboard:read.

The action needs dashboard:read, and the app has this scope. TYPO3 rejects a write action with 403 Missing scope.

The ActionContext contains the backend user of the app.

The dashboard action that serves the backend UI also serves the integration.

The integration receives the validated JSON result.

The MCP client discovers the authorization server at /.well-known/oauth-authorization-server and starts the OAuth flow.

The user logs in and approves the requested scopes on the consent screen. The token contains only the scopes that the app requested, that an administrator configured for the app and that the user can hold.

POST /typo3/api/mcp
{"method": "tools/list", …}

EXT:hub validates the token and intersects the scopes of the token with the current scopes of the app.

The MCP server is an action and needs the scope mcp.

The method tools/list returns every action with granted scopes, with the input and output schema and hints such as readOnlyHint.

{"method": "tools/call",
 "params": {"name": "fetch_dashboards"}}

The action mcp calls the target action through the same ActionInvoker, with the same user and the same scopes.

The dashboard action now serves the backend, integrations and AI agents.

TYPO3 returns the validated result as structuredContent in the JSON-RPC response. The agent can render the dashboard of the user.

vendor/bin/typo3 mcp:serve --user=editor

The MCP client starts the command and talks to the command through standard input and output.

The client and TYPO3 exchange JSON-RPC messages line by line. EXT:hub is not necessary.

The user editor must exist and be enabled. TYPO3 grants all scopes that the user editor can hold. Without --user, TYPO3 uses the CLI user _cli_.

The same MCP action handles initialize, tools/list and tools/call.

TYPO3 invokes and validates tool calls exactly as over HTTP.

The agent can do what editor can do, and nothing more.

Security model

An app can never do more than the user that the app acts for, and never more than an administrator configured for the app.

1 · Scopes of the app

An app with only content:read cannot call a write action, even if the user can.

2 · Permissions of the user

Actions run as the backend user. Page permissions, table and field access and workspaces apply as usual.

Scope calculator

The scopes of an OAuth token are the intersection of the scopes that the app requests, the scopes that an administrator configured for the app and the scopes that the user can hold. Change the values and select a user.

In an action that the token can call, the permissions of the user still apply. On every request, EXT:hub intersects the scopes of the token with the current configuration of the app again, so when an administrator removes a scope from an app, the change applies immediately.

Actions in extensions

A method of your extension becomes an action with an HTTP endpoint, OpenAPI documentation and an MCP tool.

An action is a method of a regular service in your extension. With the default Configuration/Services.yaml of an extension, TYPO3 finds the attribute automatically, and you register nothing.

1 · Attribute

Mark a public method with #[AsAction], set its name and select a scope that exists, for example content:read.

2 · Typed input and output

Typed parameters and an exact PHPDoc return type define the JSON Schema. TYPO3 validates the values and converts them.

3 · Declared errors

Throw NotFoundError or PermissionDeniedError and declare each one with @throws.

namespace MyVendor\MyExtension\Action;

use MyVendor\MyExtension\Domain\NewsRepository;
use TYPO3\CMS\Core\Action\Error\NotFoundError;
use TYPO3\CMS\Core\Attribute\AsAction;
use TYPO3\CMS\Core\Scope\ContentReadScope;

final readonly class NewsActions
{
    public function __construct(
        private NewsRepository $newsRepository,
    ) {}

    /**
     * @return list<array{uid: int, title: string, date: string}>
     */
    #[AsAction(
        name: 'my-extension/news/latest',
        summary: 'Fetch the latest news',
        scopes: [ContentReadScope::class],
    )]
    public function latest(int $limit = 10): array
    {
        return $this->newsRepository->findLatest($limit);
    }

    /**
     * @return array{uid: int, title: string, teaser: string}
     * @throws NotFoundError if the news record does not exist
     */
    #[AsAction(
        name: 'my-extension/news/{uid}',
        summary: 'Fetch a news record',
        scopes: [ContentReadScope::class],
    )]
    public function show(int $uid): array
    {
        return $this->newsRepository->findByUid($uid)
            ?? throw new NotFoundError('News not found', 1792000001);
    }
}

Custom scopes

The scopes of TYPO3 cover most cases. If an administrator must grant access to your actions separately, register a scope and reference its class in scopes.

use Symfony\Component\DependencyInjection\Attribute\AsTaggedItem;
use TYPO3\CMS\Core\Scope\ScopeInterface;
use TYPO3\CMS\Core\Scope\ScopeUser;

#[AsTaggedItem(index: 'my-extension:news:read')]
final class NewsReadScope implements ScopeInterface
{
    public function getName(): string { return 'Read access to news'; }
    public function getDescription(): string { return 'Read news records.'; }
    public function getIcon(): string { return 'content-news'; }

    // Decides whether a user may hold this scope at all
    public function allowedForUser(ScopeUser $user): bool { return true; }
}

MCP tool calls

The MCP server is the action mcp (POST /typo3/api/mcp, scope mcp). TYPO3 authenticates, checks the scopes and validates a call to the action mcp like any other call. The action mcp then calls the requested tool through the same ActionInvoker.
