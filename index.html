--- title: The TYPO3 Action API ---
Proposed for TYPO3 v15 · in review

One API for TYPO3.
Write it once, use it everywhere.

The Action API turns a typed PHP method into a feature that the TYPO3 backend, external applications and AI agents can use: validated, documented and secured, without writing a single controller. 

#[AsAction(
    type: ActionType::fetch,
    name: 'my-extension/page/{uid}/titles',
    summary: 'Fetch the titles of a page',
    scopes: [ContentReadScope::class],
)]
public function titles(int $uid): array
{
    // your business logic
}

Problems it solves

Today, every way of talking to TYPO3 is built separately. The Action API replaces these islands with one consistent model.

Today

Every backend feature has its own AJAX controller

Each controller parses arguments, validates them and formats errors in its own way.

With the Action API

One generic dispatcher. Arguments and results are validated against a schema derived from the method signature.

Today

No general-purpose API in the core

Integrations depend on extensions that each build and maintain their own endpoints.

With the Action API

Every action is an HTTP endpoint below /typo3/api/, provided by TYPO3 and extensions alike.

Today

Authorization is reinvented per integration

API keys, OAuth and fine-grained permissions are built again for every connection.

With the Action API

EXT:hub offers OAuth 2.0 and static tokens. Scopes limit apps; the user's permissions always apply.

Today

No machine-readable description

Endpoints are documented by hand, if at all, and the documentation drifts from the code.

With the Action API

An OpenAPI 3.1 document is generated from the code and browsable in Swagger UI.

Today

AI agents cannot work with TYPO3

There is no safe, standard way for assistants to read or change content on behalf of an editor.

With the Action API

A built-in MCP server offers actions as tools. Agents act as the user, limited by the granted scopes.

Today

The same logic is wrapped again for every consumer

Backend UI, integrations and automation each need their own glue code.

With the Action API

Write the feature once. Every channel is available automatically.

The concept: actions

An action is a public method of a service, marked with the #[AsAction] attribute. Its signature is the contract: TYPO3 derives everything else from it, once, when the dependency injection container is compiled.

Hover or tap the highlighted parts to see what each one becomes.

final readonly class PageTitleAction
{
    /**
     * @return list<string>7
     * @throws NotFoundError if the page does not exist8
     */
    #[AsAction(
        type: ActionType::fetch1,
        name: 'my-extension/page/{uid}/titles'2,
        summary: 'Fetch the titles of a page'3,
        scopes: [ContentReadScope::class]4,
    )]
    public function titles(
        int $uid5,
        ActionContext $context6,
    ): array {
        // …
        throw new NotFoundError('Page not found', 1791975434);
    }
}
  • 1
    Typefetch → GET, create → POST, replace → PUT, update → PATCH, delete → DELETE, dispatch → POST. Also sets MCP hints such as “read-only”.
  • 2
    NameIdentifier and route: /typo3/api/my-extension/page/{uid}/titles. Becomes the MCP tool fetch_my_extension_page_by_uid_titles.
  • 3
    SummaryDocumentation for developers in OpenAPI and for AI agents in the tool list.
  • 4
    ScopesThe caller must be granted all listed scopes, otherwise the call is rejected.
  • 5
    ParametersBecome the input JSON Schema. Values come from the route, the query string or the JSON body, and are validated and converted to PHP types.
  • 6
    ActionContextNot part of the schema. Passed in automatically: TYPO3 context, user, translator, request and granted scopes.
  • 7
    Return typePHPDoc types like list<string> or array shapes become the output schema. The result is validated before it is returned.
  • 8
    Declared errorsErrors must be declared with @throws. NotFoundError becomes a documented 404, PermissionDeniedError a 403.

One action, every channel

The example action above, as each consumer sees it. Nothing on this list requires additional code.

Backend modules call actions through a small client. It adds the bearer token bound to the logged-in user, so a session cookie alone is never enough.

import { action } from '@typo3/core/action/request.js';

const response = await action('/my-extension/page/{uid}/titles', { uid: '42' }).get();
const titles = await response.resolve();

External applications use the same endpoint with a token from EXT:hub. Declared errors arrive with their status code.

curl -H 'Authorization: Bearer <token>' \
    https://example.org/typo3/api/my-extension/page/42/titles

# 200 OK
["Home", "Startseite", "Accueil"]

# 404 Not Found
{"error": "Page not found"}

Security model

An application is never more powerful than the user it acts for, and never more powerful than the administrator configured it to be.

1 · Scopes decide which actions an app may call

An app with only content:read cannot call a write action, even if the user could.

2 · The user’s permissions decide what an action may do

Actions run as the backend user. Page permissions, table and field access and workspaces apply as usual.

Try it: which scopes does an OAuth app get?

The scopes of an OAuth token are the intersection of what the app requests, what an administrator configured for the app and what the user may hold. Toggle the values and pick a user.

What the app can call

Within an allowed action, the user’s own permissions still apply. On every request, the token’s scopes are intersected with the app’s current configuration again, so removing a scope from an app takes effect immediately.

Build your own action

Three steps for extension developers.

1 · Write the method

A public method of a service with typed parameters, a precise return type and #[AsAction]. Inject ActionContext if you need the user or request.

2 · Declare errors

Throw NotFoundError, PermissionDeniedError or your own ActionExceptionInterface and declare each one with @throws.

3 · Pick or add a scope

Reuse content:read or content:write, or register your own scope.

use Symfony\Component\DependencyInjection\Attribute\AsTaggedItem;
use TYPO3\CMS\Core\Scope\ScopeInterface;
use TYPO3\CMS\Core\Scope\ScopeUser;

#[AsTaggedItem(index: 'my-extension:news:read')]
final class NewsReadScope implements ScopeInterface
{
    public function getName(): string { return 'Read access to news'; }
    public function getDescription(): string { return 'Read news records.'; }
    public function getIcon(): string { return 'content-news'; }

    // Decides whether a user may hold this scope at all
    public function allowedForUser(ScopeUser $user): bool { return true; }
}

That is all. Without further code, the action is available

  • as /typo3/api/… endpoint for the backend and external apps,
  • in the OpenAPI document and Swagger UI,
  • as MCP tool for every client that holds the required scopes,
  • with validated input and output and documented errors.

MCP: an action calling actions

The MCP server is the action mcp (POST /typo3/api/mcp, scope mcp). Authentication, scope checks and validation apply to it like to any other action. Inside, it calls the requested tool through the same ActionInvoker.
