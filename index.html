    One API for TYPO3.
    Write it once, use it everywhere.

    The Action API turns a typed PHP method into a feature that the TYPO3 backend, external applications and AI agents can use: validated, documented and secured, without writing a single controller.

    #[AsAction(
    type: ActionType::fetch,
    name: 'my-extension/page/{uid}/titles',
    summary: 'Fetch the titles of a page',
    scopes: [ContentReadScope::class],
)]
public function titles(int $uid): array
{
    // your business logic
}
    ➜
    Write onceOne PHP method serves the backend, integrations and AI agents.
    Typed and validatedJSON Schema derived from PHP types; input and output are checked.

    Problems it solves

    Today, every way of talking to TYPO3 is built separately. The Action API replaces these islands with one consistent model.

    Each controller parses arguments, validates them and formats errors in its own way. One generic dispatcher. Arguments and results are validated against a schema derived from the method signature. Integrations depend on extensions that each build and maintain their own endpoints. Every action is an HTTP endpoint below /typo3/api/, provided by TYPO3 and extensions alike. API keys, OAuth and fine-grained permissions are built again for every connection. EXT:hub offers OAuth 2.0 and static tokens. Scopes limit apps; the user’s permissions always apply. Endpoints are documented by hand, if at all, and the documentation drifts from the code. An OpenAPI 3.1 document is generated from the code and browsable in Swagger UI. There is no safe, standard way for assistants to read or change content on behalf of an editor. A built-in MCP server offers actions as tools. Agents act as the user, limited by the granted scopes. Backend UI, integrations and automation each need their own glue code. Write the feature once. Every channel is available automatically.

    The concept: actions

    An action is a public method of a service, marked with the #[AsAction] attribute. Its signature is the contract: TYPO3 derives everything else from it, once, when the dependency injection container is compiled.

    Hover or tap the highlighted parts to see what each one becomes.

    final readonly class PageTitleAction
{
    /**
     * @return list<string>
     * @throws NotFoundError if the page does not exist
     */
    #[AsAction(
        type: ActionType::fetch,
        name: 'my-extension/page/{uid}/titles',
        summary: 'Fetch the titles of a page',
        scopes: [ContentReadScope::class],
    )]
    public function titles(
        int $uid,
        ActionContext $context,
    ): array {
        // …
        throw new NotFoundError('Page not found', 1791975434);
    }
}
    fetch → GET, create → POST, replace → PUT, update → PATCH, delete → DELETE, dispatch → POST. Also sets MCP hints such as “read-only”. Identifier and route: /typo3/api/my-extension/page/{uid}/titles. Becomes the MCP tool fetch_my_extension_page_by_uid_titles. Documentation for developers in OpenAPI and for AI agents in the tool list. The caller must be granted all listed scopes, otherwise the call is rejected. Become the input JSON Schema. Values come from the route, the query string or the JSON body, and are validated and converted to PHP types. Not part of the schema. Passed in automatically: TYPO3 context, user, translator, request and granted scopes. PHPDoc types like list<string> or array shapes become the output schema. The result is validated before it is returned. Errors must be declared with @throws. NotFoundError becomes a documented 404, PermissionDeniedError a 403.

    One action, every channel

    The example action above, as each consumer sees it. Nothing on this list requires additional code.

    Backend modules call actions through a small client. It adds the bearer token bound to the logged-in user, so a session cookie alone is never enough.

    import { action } from '@typo3/core/action/request.js';

const response = await action('/my-extension/page/{uid}/titles', { uid: '42' }).get();
const titles = await response.resolve();

    Security model

    An application is never more powerful than the user it acts for, and never more powerful than the administrator configured it to be.

    1 · Scopes decide which actions an app may call

    An app with only content:read cannot call a write action, even if the user could.

    2 · The user’s permissions decide what an action may do

    Actions run as the backend user. Page permissions, table and field access and workspaces apply as usual.

    Try it: which scopes does an OAuth app get?

    The scopes of an OAuth token are the intersection of what the app requests, what an administrator configured for the app and what the user may hold. Toggle the values and pick a user.

    Backend user who grants access

    What the app can call

    Within an allowed action, the user’s own permissions still apply. On every request, the token’s scopes are intersected with the app’s current configuration again, so removing a scope from an app takes effect immediately.

    Build your own action

    Turn a method of your extension into an action: an endpoint, documentation and an AI tool, in a few lines.

    An action is a method of a regular service in your extension. With the default Configuration/Services.yaml of an extension, nothing needs to be registered: the attribute is picked up automatically.

    1 · Add the attribute

    Mark a public method with #[AsAction], give it a name and pick an existing scope such as content:read.

    2 · Type input and output

    Typed parameters and a precise PHPDoc return type become the JSON Schema. Values are validated and converted for you.

    3 · Declare errors

    Throw NotFoundError or PermissionDeniedError and declare each one with @throws.

    namespace MyVendor\MyExtension\Action;

use MyVendor\MyExtension\Domain\NewsRepository;
use TYPO3\CMS\Core\Action\Error\NotFoundError;
use TYPO3\CMS\Core\Attribute\AsAction;
use TYPO3\CMS\Core\Scope\ContentReadScope;

final readonly class NewsActions
{
    public function __construct(
        private NewsRepository $newsRepository,
    ) {}

    /**
     * @return list<array{uid: int, title: string, date: string}>
     */
    #[AsAction(
        name: 'my-extension/news/latest',
        summary: 'Fetch the latest news',
        scopes: [ContentReadScope::class],
    )]
    public function latest(int $limit = 10): array
    {
        return $this->newsRepository->findLatest($limit);
    }

    /**
     * @return array{uid: int, title: string, teaser: string}
     * @throws NotFoundError if the news record does not exist
     */
    #[AsAction(
        name: 'my-extension/news/{uid}',
        summary: 'Fetch a news record',
        scopes: [ContentReadScope::class],
    )]
    public function show(int $uid): array
    {
        return $this->newsRepository->findByUid($uid)
            ?? throw new NotFoundError('News not found', 1792000001);
    }
}

    That is all. Without further code, both methods are available:

    Backend JavaScriptaction('/my-extension/news/latest', {}).get()
    HTTP APIGET /typo3/api/my-extension/news/latest?limit=5 and GET /typo3/api/my-extension/news/42
    OpenAPIBoth operations with parameters, response schemas and the documented 404
    MCP toolsfetch_my_extension_news_latest and fetch_my_extension_news_by_uid, for every client that holds content:read
    Validationlimit must be an integer, results must match the declared array shapes
    Optional: a scope of your own

    The scopes shipped with TYPO3 cover most cases. If an app should be able to get access to your actions separately, register a scope and reference its class in scopes.

    use Symfony\Component\DependencyInjection\Attribute\AsTaggedItem;
use TYPO3\CMS\Core\Scope\ScopeInterface;
use TYPO3\CMS\Core\Scope\ScopeUser;

#[AsTaggedItem(index: 'my-extension:news:read')]
final class NewsReadScope implements ScopeInterface
{
    public function getName(): string { return 'Read access to news'; }
    public function getDescription(): string { return 'Read news records.'; }
    public function getIcon(): string { return 'content-news'; }

    // Decides whether a user may hold this scope at all
    public function allowedForUser(ScopeUser $user): bool { return true; }
}

    MCP: an action calling actions

    The MCP server is the action mcp (POST /typo3/api/mcp, scope mcp). Authentication, scope checks and validation apply to it like to any other action. Inside, it calls the requested tool through the same ActionInvoker.
